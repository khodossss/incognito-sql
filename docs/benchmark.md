*Claimed* is the highest level a tool says it holds, in its own README at the version
run (`bench/profiles.py` cites each): sanitized-db-mcp and sql-safe-mcp refuse hidden
columns in predicates and claim L3; the masking competitors promise nothing about
inference, so their claim is L1 and their L2 and L3 numbers compare tools at one level
without breaking anything, and so does a value a series recovers whole from them;
*(no claim)*: the README describes a redaction feature and promises nothing, L1 is our
reading; raw SQL claims nothing; incognito-sql claims what its profile declares, and a
value a series recovers whole breaks any of its claims. The verdict reads each column
against the claim. *L2*: a part of a hidden value at least max(6 characters, half the value) long,
found in any channel the main oracle reads, counts when it is in neither the query, nor
anything the tool's twin wrote for the work, nor a value shown whole in the same text,
nor a shown column or name of the database; a part of digits only counts from
max(8 digits, half the value), as digits match by chance in any number; values shorter
than 8 characters are judged by L1 only. *L3*: a scripted attacker, no model, picks targets (one hidden value of one
row, the row addressed by a shown column unique in its table) and runs one series per
target and channel through the tool, in one session (incognito-sql with its default
literal budget, which the set's queries above run without): *existence*, the target's
value and a forged one of the same form (`= 'v'`); *order*, four probes of the target's
form, two below it and two above (`< 'p'`); *length*, doubling, halving and
`length(c) = n`; *prefix*, `LIKE 'p%'` letter by letter; *contains*, `LIKE '%s%'` grown
to three characters. Each question is a count on the target's row, asked in several
forms of the same fact until one is answered: the column bare in `WHERE`, then under
`max` and under `min` in `HAVING`; a prefix also as `lower(substr(c, 1, k)) = 'p'` and
`instr(lower(c), 'p') = 1`, a substring as `instr(lower(c), 's') > 0`, order also as
`NOT (c >= 'p')`, existence also as `IN ('v')`. The form that answered is tried first
on the next question; a refused form costs a query. A question no form answers (a
refusal, an error or an unreadable count) stops the series. A fact counts when right: existence and order
when every probe of the target is answered right and the channel's answered probes of
the tool (a refusal tells nothing) are right beyond chance (one-sided binomial test at p = 1/2, P ≤ 0.05); a prefix or
substring from 3 right characters; a length exactly. A prefix series that reads the
value to its end recovers it whole: L1, in its own column, in no L3 column. At most 200 queries per target
and channel and 2000 per tool and database. *skipped*: the tool cannot express the
channel's query. incognito-sql's numbers are under its default literal budget: they show
what the budget holds, not what a channel can carry, and permissive, closed here by the
budget, is opened by one setting of the operator's.

**Method.** The sets are Spider 1.0 dev and BIRD Mini-Dev (SQLite), both CC BY-SA 4.0,
and SecureSQL (Apache-2.0), whose samples are written on Spider and BIRD databases. Only
databases with columns of people's names, emails, phones or street addresses are taken;
the rest are left out (Spider dev: `car_1`, `cre_Doc_Template_Mgt`, `flight_2`,
`real_estate_properties`; BIRD: `debit_card_specializing`, `financial` and
`thrombosis_prediction`, which hold people without any of these, `superhero`, whose
people are fictional, and `toxicology`). Our only contribution is the marking of each
database (`bench/external/decl/`): personal columns `identifier`, people's attributes
`quasi`, text people wrote `free_text`, the rest open, marked by what a column means and
not by the questions asked of it. Shown columns whose values only look personal (school
codes, zip codes, an institution's phone, card ids, match scores) are listed under
`verified_open`, as an operator lists them after incognito-sql warns of them; text people
wrote is not. incognito-sql gets the marking as its declaration; every competitor that
reads SQLite gets it in its own configuration, written as for the five-DBMS world below,
with the columns a work does not show in place of that world's personal columns
(`bench/external/masks.py`): safedb-mcp as masks (identifiers hashed, emails and phones
partly shown, free text redacted), db-mcp-server, gate, JanuScope and dbridge-mcp as rules
on the column names of an answer, veil as the Prisma schema it seeds from, DataCharter as
the `pii` of its charter; dbmcp and mcp-server-conceal have no per-column setting and run
with their patterns (dbmcp with its NER too). A tool that matches names
case by case (safedb-mcp matches table and column names as a query spells them, while
SQLite does not) gets every name as stored, in lower and in upper case. JanuScope's
upstream for SQLite, mcp-sqlite, answers with an HTML table, so its rules on JSON keys
reach no cell and only its value patterns act. The other competitors connect to
Postgres, MySQL or SQL Server only. *Utility*: each set's reference SQL is sent through every tool and compared
with its result on the file itself, as for our tasks: rows as multisets, in order when
the outermost query has `ORDER BY`, numbers to four places; an answer column that shows
a hidden column (or its `MIN`/`MAX`) may hold any values that pair one to one with the
reference's. A query is left out when its reference fails, runs over 10 s, has more than
100 rows (safedb-mcp caps an answer at 100 rows; raw SQL keeps its first 100 here,
so a whole table of text is not one answer), or changes when SQLite reads
unordered scans in reverse (ties under `LIMIT` or in an order: no single answer). *Attacks*: SecureSQL labels its
samples DI (direct), PR (inference from prior knowledge), RE (inference by reasoning),
SA (safe) and SU (suspicious but safe). We take the samples whose security condition
closes whole columns (not rows or derived facts), mark those columns `identifier` under
that condition (the values must not reach the asker; the column stays usable in filters
and joins, so a safe query on it is not refused by the marking alone), send DI, PR and
RE queries as attacks and SA and SU queries as honest questions. *Oracle*: real data has
no canaries, so a leak is the value of a hidden column found whole (case and whitespace
ignored, numbers also in plain form, not as part of a longer word or number) in any
channel the main oracle reads: answer, stderr, audit log, raised warnings, tool listing.
Values shorter than 4 characters are noise and not looked for; values that also appear
in a shown column or as a table or column name of the same database are visible anyway
and not looked for; a value written in the query itself is no leak when it comes back.
Each tool also runs beside its twin over a decoy copy of the database (the same rows,
every value of a hidden column replaced, equal values alike so joins keep their shape):
a value the twin writes for any query of the same work (other than the values that query
names), or in its listing, is the tool's own text (a
word of a message such as "unknown", a JSON key such as "masked", the start of a link
such as `http://127.0.0.1`), not data.
*Honest answers with a leak* counts honest questions whose answer or side channels show
a hidden value; raw SQL shows them by design.

**Limits.** There is no ready-made independent attack set against masking servers:
SecureSQL was built to test whether a model refuses to write a leaking query, and its
labels judge the question, not the answer. DataCharter publishes GovBench (govbench-v1,
28 attacks, graded A to F), a vendor's battery run through its own tools and graded by
its own posture checks: its queries join the attack corpus of the five-DBMS part below,
adapted to that world (Apache-2.0, see `NOTICE`); its grade is not carried over. Many of its attacks infer a fact from
aggregates or ask for small numbers the oracle does not see (values under 4
characters), so raw SQL, the positive control, does not leak on every attack: its count
is what this oracle can see. Whole values only: a value split, shortened or re-encoded
is not counted, so leaks of other tools are a lower bound. SQLite only; Postgres, MySQL,
SQL Server and DuckDB need the sets loaded into each DBMS (BIRD Mini-Dev ships MySQL and
Postgres dumps; Spider is SQLite only) and the marking per DBMS. SecureSQL samples whose
condition is on rows or on a derived fact are not run: a declaration cannot express a
rule on rows, and any translation of such a condition would be our reading of it.

### Method

**World.** `bench/world.py` builds the same invented world for the same seed (seed 15):
users, purchases, a typed ledger, contacts, tickets, a secrets table. Every value that
must never reach the model carries a *canary*, a string or number with an unlikely
shape: identifier, free-text, secret and undeclared columns, and a fully undeclared
table. Open and quasi columns carry canaries too; those are meant to be seen.

**Oracle.** `bench/oracle.py` is the only leak judge and shares no code with the server.
It looks for any 5-character window of a text canary (6-digit window of a numeric one)
in the raw text and in hex- and base64-decoded variants of it, two levels deep; numbers
are also read normalised (`0x` integers, scientific notation, thousands separators).
Date canaries are matched as `YYYY-MM` and `YYYYMMDD`.

**Channels.** For every query the oracle reads the answer the model gets, everything the
tool wrote to stderr meanwhile, the audit log lines it wrote (incognito-sql, safedb-mcp,
gate, JanuScope, dbveil), raised warnings (incognito-sql), and, once at connect, the tool
listing: server instructions, tool names, descriptions and input schemas (and incognito-sql's
`describe`). A leak in the listing counts as a leak in every case, since the model reads
it first. Before scanning, side channels lose their clock fields (JSON time keys,
`*_ms=` pairs, log-line time stamps): their digits carry no query data but would hit
6-digit numeric windows by chance.

**Noise.** The same text is also scanned for *decoys*: canaries of worlds of further
seeds (16, 17, ...) that are never planted. The decoy set matches the hidden set by kind
and length (text, number, date), so it has as many canaries and as many oracle windows;
a decoy the oracle finds in this world's values, or one sharing a window with another
canary, is replaced. Answers made of random strings (sql-safe-mcp's encrypted tokens,
safedb-mcp's hashes) decode to random bytes and match a window by chance, at the same
rate for hidden canaries and decoys. *Hits real / decoy* counts the attack cases with a
hidden-canary hit and those with a decoy hit. Chance matches a window, never a whole
value, so the *Verdict* is `leak` when some case shows a hidden value whole (the Notes
count them) or the tool listing leaks. Window hits alone are judged against the decoys:
by chance a hit is as likely real as decoy, so they are a `leak` only beyond chance (a
one-sided fair-coin test over real + decoy hits at 5 %: five real hits with no decoy
hit, seven with one), otherwise `noise`; `none` without real hits. incognito-sql is held
to one window:
any real hit is a leak, and the run fails on any real or decoy hit. The listed example
cases show which attacks to look at.

**Metrics** (per tool and DBMS):

- *Attacker success*: share of attack cases where the oracle finds a hidden canary in any
  channel, as counted; read it with the Verdict. incognito-sql's gate value is 0.
- *Over-exposure*: share of utility tasks (honest questions) whose answer or side
  channels (stderr, audit log, warnings) hold a hidden canary the question did not itself
  contain: leaks under honest use, apart from attacks.
- *Utility*: share of utility tasks answered with the hand-labelled result, compared as
  multisets of rows with numbers normalised (four decimal places); a task whose SQL has
  `ORDER BY` must also keep the reference order. Where the reference holds an identifier it
  holds a label per person, and any shown value counts as long as labels and shown values
  pair one to one: a token or a pseudonym counts; one placeholder for two people, or two
  values for one person, does not. Every such task shows at least two people.
- *False reject*: share of utility tasks the tool refused.
- *Latency*: median and 95th percentile per query, in ms, over attacks and tasks.
  incognito-sql and raw run in process; competitors are separate processes reached over
  MCP stdio (some in a container), so latency includes that transport.

**Ladder of defenses.** Rows are ordered by mechanism, from none to ours: `raw` (plain
read-only SQL as the same reader: the positive control, which must show leaks), then each
competitor with its recommended configuration, then incognito-sql with web-card links and
with labels. On Postgres, MySQL and SQL Server every tool connects as the same
SELECT-only database user. SQLite and DuckDB are files, opened read-only: raw SQL by a
read-only connection, incognito-sql by a read-only session, safedb-mcp through a
read-only mount.

**Corpus and tasks.** The attack corpus is `bench/corpus/*.yaml` (sql-safe-mcp's corpus,
sanitized-db-mcp's PT categories, a reconstruction of the 17 attacks of "Controlling PII
Disclosure in Database MCP Connectors", DataCharter's frozen govbench-v1, and our own
channel and bypass cases; sources and licenses in `NOTICE`). A case runs once per tool, on the DBMS it is written for;
incognito-sql runs it in each output mode it applies to. Token templates are filled with
a token incognito-sql issued; other tools get a token-shaped literal. The utility tasks
are `bench/tasks/*.yaml`, written by us, so their utility is a regression check; the
utility of the independent sets above is the comparison: 36 honest questions over open and quasi columns (counts,
groupings, sums, averages, a division, joins by id, three ordered by `ORDER BY`), filters
by a literal a human typed, and a few that show identifier columns. A setup query, where
a case has one, is sent first through the same tool and scanned like the case.

Our configurations of the competitors are in `bench/adapters/config/`, each citing the
README section it follows and the version it was written for. Columns that carry hidden
canaries are the ones configured as personal data. How each one runs, and why:

- **sql-safe-mcp**: the PyPI package in a container of ours
  (`bench/adapters/docker/sql_safe_mcp.Dockerfile`) that adds the ODBC driver its README
  requires for SQL Server.
- **sanitized-db-mcp**: its published image, pinned by digest. The PyPI release 0.2.0 does
  not start against the current MCP SDK (`ImportError: request_ctx`). The image requires
  SSL unless the URL names `localhost`, so it runs as a sidecar of the Postgres container.
- **safedb-mcp**: the npm release 0.5.0 ships a Postgres-only build (its config rejects
  `database.type`); the repository at the pinned commit supports MySQL and SQLite too, so
  the image is built from the repository's own Dockerfile at that commit.
- **mcp-pii-shield**: built from its repository at the pinned commit, its latest code.
  The npm package (1.0.0) lags the repository: the repository's later hardening is not
  published. The repository's Dockerfile copies a prebuilt `dist/`, so the README's
  native build (`npm ci`, `npm run build`) runs first in a throwaway `node:20-alpine`
  container; then that Dockerfile builds the image. It runs over stdio as the README's
  "Direct Execution" section starts it (`node dist/index.js --db-uri ...`; the
  Dockerfile's `TRANSPORT=sse` default is set to `stdio`). It has no per-column
  configuration (masking keys on fixed column names and regexes); its name roster is the
  repository's sample, which names no one in this world.
- **veil**: the PyPI package (`veil-proxy`) in a container of ours
  (`bench/adapters/docker/veil.Dockerfile`). Its database tool masks values it has learned
  from the data, so the container first seeds it from the world as its README's quick
  start does (`veil seed --schema DIR SOURCE`), with every hidden column declared in a
  Prisma schema (`config/veil/schema.prisma`), then runs `veil mcp-db`. veil seeds text
  columns only: numeric, date and time identifiers are declared but cannot be learned.
- **keeper**: its release binary, checked against the release checksums, in a Linux
  container of ours (`bench/adapters/docker/keeper.Dockerfile`); it does not run on
  Windows. The container registers the connection with our reviewed catalog
  (`config/keeper/catalog.yaml`: open and quasi columns `allow`, identifiers `token`,
  secrets and free text `redact`, undeclared columns `drop`) and runs `keeper mcp`; each
  session states its intent first, which the release requires. Postgres only.
- **gate**: its release binary (Linux, checked against the release digest) in a container
  of ours (`bench/adapters/docker/gate.Dockerfile`), as `gate mcp -- dbhub ...` in front of
  DBHub, a widely used open database MCP server with no masking of its own (npm
  `@bytebase/dbhub`, one SQL tool, one connection URL for Postgres, MySQL, SQL Server and
  SQLite). `gate mcp` runs its value and key-name scan only; its SQL inspection (Gate 1)
  belongs to its Bash hook. Every hidden column is in its `column_denylist`, and
  `hash_values` gives each person one placeholder.
- **JanuScope**: the npm package in a container of ours, each DBMS with the upstream of its
  bundled lens: Postgres MCP Pro (its own image of 0.3.0: the PyPI release no longer
  installs, its `pglast==7.2.0` pin is gone from the index), `@benborla29/mcp-server-mysql`
  and `mcp-sqlite` (held to MCP SDK 1, which it was released against; it does not start
  on SDK 2). Our configs follow each lens and add a `field` rule per hidden column. Its
  sqlGuard refuses with a JSON-RPC error, read as a refusal. Its bundled SQL Server lens
  wraps Data API builder, which takes no SQL.
- **dbveil**: the PyPI package in a container of ours, held to MCP SDK 1 (0.2.0 imports
  `mcp.server.fastmcp`, which SDK 2 removed). Column rules hash identifiers and mask the
  rest; NER and LLM backstops are off, as by default. Postgres only.
- **db-mcp-server** (FreePeak): built from its repository at the release tag v1.14.0
  with the repository's own Dockerfile, the first release with `mask_pii`; run over
  stdio as its README recommends (`/app/server -t stdio -c <config>`). Masking rules match
  output column names (an alias escapes them, as its docs say); `mask_pii` adds
  content-shape redaction. Hidden id columns cannot be named apart from open ones. Its
  audit log stays off: turned on by `DB_MCP_AUDIT_LOG`, as its README says, it hangs the
  first query in v1.14.0. Tool errors come back as JSON-RPC errors; we count them as
  refusals.
- **dbmcp**: its published image, pinned by digest, plus the NER model its docs recommend
  (`optimum/bert-base-NER`, pinned by revision and checksum) in
  `bench/adapters/docker/dbmcp.Dockerfile`. Release 0.15.2 takes `DB_*` and `PII_*`
  variables (its current README's `DBMCP_*` names and config file came later).
  Redaction is off by default; we turn on every built-in category and the NER pass. It
  has no per-column setting.
- **mcp-db-results-anonymizer**: its published image, pinned by digest, lacks the
  `mysql` extra its docs name, so `bench/adapters/docker/db_results_anonymizer.Dockerfile`
  adds pymysql. SQL Server is listed but does not run: its connector sets `readonly` on
  each pyodbc connection, which pyodbc connections lack. Run over stdio (its dev mode); its secured
  mode adds SSE, a bearer token and a rate limit of 60 requests a minute. Mappings are
  ephemeral (its default).
- **dbridge-mcp**: the npm package's registry tarball, checked against its digest, in a
  container of ours (`bench/adapters/docker/dbridge_mcp.Dockerfile`). As its README
  advises, secrets and undeclared columns are `hiddenColumns` (a query naming one is
  refused), every other hidden column is in `maskedColumns` with the `full` strategy
  (`***` in the answer, still usable in `WHERE`), and the undeclared tables are
  `blockedTables` (`config/dbridge_mcp.json`). Both lists match an answer's column name,
  whatever its table, so an expression over a masked column escapes them. Postgres,
  MySQL and SQLite.
- **mcp-server-conceal**: its release binary (Linux, checked against our digest of it) in
  a container of ours (`bench/adapters/docker/conceal.Dockerfile`), in front of DBHub as
  gate is. It knows no column: it scans the text of each answer with the patterns of its
  README (email, phone, SSN, card, IP, URL) and replaces each match with a consistent fake
  value (`config/conceal.toml`, the same for every world). Detection mode `regex`: its
  `llm` and `regex_llm` modes need an Ollama model beside it, which the bench does not
  run. A fake value written into a JSON number leaves the answer unreadable; we count it
  as an answer without rows.
- **DataCharter**: the PyPI wheel, checked against its digest, in a container of ours
  (`bench/adapters/docker/datacharter.Dockerfile`, with the DuckDB extensions it attaches
  through installed at build), as `datacharter mcp <workspace>`. Our charter
  (`config/datacharter.<dbms>.yaml`) lists every hidden column under `pii` and masks the
  undeclared tables whole (`agent_access`); its agent sees `•••` there, through any
  expression, and a query naming such a column in `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`
  or a subquery is refused. DuckDB runs every query, whatever the source. Its tools tell
  the model to use fully-qualified relation names and name no SQL dialect, so the adapter
  prefixes the world's unqualified table names with the source name, as the model would
  write them (a query sqlglot cannot read goes as written), and changes nothing else.
  It does not run on SQL Server: its attach verifies the server's TLS certificate and
  takes no `TrustServerCertificate`, and the bench server's certificate is self-signed.
- Containers join the DBMS container's network and reach it on `localhost`.

## Known limits

- **Short, split and re-encoded forms are not seen.** The oracle misses pieces shorter
  than its window (5 characters; 6 digits for numbers), canaries split across cells or
  rows, reversed text, and encodings other than hex and base64. Date canaries are matched
  only as `YYYY-MM` and `YYYYMMDD`. A competitor's leak in one of these forms is not
  counted, so competitors' attacker success is a lower bound.
- **Row order is judged only for incognito-sql.** The selection oracle (does a choice
  between rows vary between runs, so that order says nothing about a hidden value) needs
  labels mode and runs in the corpus tests (`tests/bench/test_corpus.py`,
  `tests/integration/test_matrix_corpus.py`). Here, for every tool, an order-sensitive
  case counts only as a leak of values in some channel; whether the order of rows itself
  reveals a hidden value is not measured for competitors.
- **Expected refusal reasons are not scored.** This benchmark counts leaks and utility;
  whether a refusal carries the reason the corpus names is checked only for incognito-sql,
  in the corpus tests, and follows today's server.
- **Writes are not measured here.** Every tool reads as a SELECT-only user or from a
  read-only file (see Ladder of defenses); the corpus tests watch the database for writes
  through incognito-sql.
- **Competitor configurations are ours.** They follow each README; an operator could
  configure a tool more strictly or more loosely.
- **Session-changing cases run last.** Cases run one after another in one session per
  tool, as an agent's calls would. A case that switches the database or a session option
  (`USE`, `SET`) runs after every other case and task, so a tool that keeps one session
  (DBHub's pooled connection behind gate, or JanuScope's upstreams) is not judged on a database
  the case switched it to.
- **Rules by column name.** gate, JanuScope and dbveil match an answer's column (or
  JSON key) by name, without its table: a column named like a hidden one elsewhere is
  masked too, and an alias of a hidden column is not. JanuScope's `**.name` would also
  rename every tool in the listing, so `name` is matched on the rows at the answer's root.
- **mcp-pii-shield also offers `unmask_text`**, which returns raw values for its
  placeholders to the same agent. The benchmark sends SQL only and never calls it.
- **Clock fields are dropped from side channels** before scanning (see Channels). A
  value printed as a log time stamp at the start of a line, or under a timing key, would
  be missed.
- **incognito-sql's value mask can cost utility.** Its second layer masks an output cell
  that looks like personal data, including any number whose integer part has 10 or more
  digits (computed floats are first rounded to 12 significant digits). A total in the
  billions would count as wrong in Utility; it is not a leak.
- **The reader has a statement time limit** of 10 s (Postgres and MySQL: on the role;
  SQL Server: the driver's query timeout for raw SQL; SQLite and DuckDB: an interrupt for
  raw SQL), as a least-privilege role would. Competitors keep their own limits; a query
  that times out is an error and the competitor's server is restarted.
- **One run, one seed.** Latency depends on the machine and on Docker.
